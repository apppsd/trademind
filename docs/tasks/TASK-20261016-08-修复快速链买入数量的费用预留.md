## 实施记录
### 二轮实施：增仓累计目标修复（2026-10-26，Claude Code，夜间授权批次）

**根因**（17-03 反例复核确认）：BUY 尺寸器把"剩余市值余量"（`cap − 当前市值`）直接除 equity 当**累计**目标权重，已有仓位时 `target ≤ cw` 恒成立 → 永远 WAIT `no lawful increase size`。

**修复**（src/trademind/agents/fast_pipeline.py，BUY 分支重写）：
1. `pos_value`/`total_value` 改从**账本快照**取（精确 Decimal，不再经 context 权重的两次除法往返）；目标=累计权重 `(pos_value+整手增量)/equity`，增量同时受市值余量（整手向下）与含费现金预算（先整手取整、再逐手验费，修复过程中发现的初版分数手缺陷一并钉住）约束。
2. 边界感知循环：28 位 Decimal 舍入不得吞掉边际一手（Guard 推导不足时按 ulp 上调候选权重）；目标不得**严格越过** Guard 单票上限权重（越界则主动降一手，仍合法时才发射，否则显式 WAIT）——Guard 保持独立硬否决，不充当缩量器。
3. `test_incomplete_valuation_vetoes_new_buy` 按 17-02 收口预案放宽可买前提（单票/总上限 450/600，注释说明），Guard 估值否决覆盖保留、断言未删。

**验证**：新增 3 项回归——17-03 原反例（100份@1.50、300/450、equity 499.90：由 WAIT 转为 BUY 1 手/Guard ALLOW/订单生成）、现金预算不足一手时显式 WAIT、单票上限耗尽时显式 WAIT。定向 4 套件 84 项通过；**全量 pytest 783 项 0 失败（exit 0，2026-10-26 本机实测）**。此前全量基线 780 项（同日修复前实测）。

**未验证**：真实盘中增仓行为随 09-09/22-01 验收；本轮零联网、零模型调用、零账本写入。

## 实施记录（2026-10-17，Claude Code 认领实施）

**根因与修复**（src/trademind/agents/fast_pipeline.py）：`available`（现金-预留-最低现金）直接当新增市值上限，未容纳买入手续费→边界上手数被Guard以min_cash_reserve_violation拒绝。修复分两层：
1. **目标计算**：市值目标保持分数（Guard早期VETO看到与修复前相同的intent形状），但钳到"现金可行的最大整手"——从`floor((cash_cap/price)/lot)*lot`向下找到`notional+compute_fees≤cash_cap`的最大手数；市值上限（单票/总敞口）比较的是市值，**不含费**（与Guard口径一致，不把合法买入误缩成WAIT）。
2. **一手前置检查对称修正**：`minimum lawful lot`改为"notional≤市值上限 且 notional+fees≤现金预算"，不再把含费needed与市值上限比较。

**验证**：tests/test_fast_decision.py新增3项——Issue复现场景（1000/100/900@1.5：修复前target0.9→VETO；修复后qty=500、target=0.75、Guard ALLOW、订单生成）、市值上限精确边界不含费缩减（150→1手照常BUY）、现金预算不足一手时明确WAIT（前置理由）；fast_decision/fast_architecture_repairs/t0_risk_guard/dual_model_pipeline套件全绿（含间接依赖该分支的全部既有测试）。
