## 接收协议
1. 首次与每次恢复先查Git/AGENTS和active Handoff，读README、docs/project/index.md、docs/project/current-status.md、docs/tasks/index.md及docs/issues/index.md；先读本Task，再按需读变更的Task/Issue，实施前补读AGENTS指定需求/架构。
2. 在自己现有会话内使用平台原生调度；若已有等价监听就复用，登记唯一标识、有效间隔/状态/接收会话及运行条件。没有调度能力就明确“未启用/等待平台支持”，不能仅在回复中承诺持续在线，也不靠无限shell sleep循环占住终端。
3. 维护本Task下方的“执行端检查记录”：最近检查时间（带Asia/Shanghai偏移）、查看的Task ID与状态/Owner、相关正文指纹或更新时间、正在实施ID/阻塞、下次入口。只存脱敏元数据，不复制全仓库内容；无变化不反复刷新文档/通知。退回in_progress的本人任务同样是待处理输入。
4. 优先继续自己已认领、依赖可满足的在途/退回任务；否则按优先级选择pending且Owner为空、依赖满足的任务。开工前重新读取文件确认无人认领，将状态/Owner/确切文件/Worktree和逐文件文档契约写回并同步索引；同文件或范围冲突先划边界，不能抢占他人Owner。队列中的未来任务不是对超出原授权行动的自动许可。
5. 修复先复现原Issue、执行必要离线测试，更新实现Task/Issue及受影响当前事实/架构/索引，跑check_docs与空白检查，记录实际命令、版本、未验项。completed只表示本端交付声明；审查端会独立复验，退回后保留原Owner继续处理，不能只改状态或验收文字求过。
6. 本端完成阶段/遇阻后重新检查队列。没有可执行事项时等待；不为了持续运行制造任务，不将检查次数等同实现进度。只在交付、失败、重要阻塞或需要用户介入时通知，无变化静默。两端通过仓库文档交接，不擅自新建/派发其他聊天。
7. 任何“退回”先读反例并核对实际需求；实现确已满足但验收存在歧义时记录证据供审查，而不是篡改原标准。最新状态以实际源码/测试优先，不把其他会话“全通过”当自己已复验。
