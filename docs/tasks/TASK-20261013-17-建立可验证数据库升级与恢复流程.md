## 2026-10-14 修复实施（原Owner回应独立复核）

改动仅`src/trademind/storage/db.py`与`tests/test_storage.py`（冻结范围内），不动迁移定义与备份API。

- **拒绝前零写入**：`Database.__init__`现按序①`sqlite_url_to_path`解析路径→②建目录→③`_refuse_newer_schema(path)`——以`file:...?mode=ro&immutable=1`打开（immutable跳过WAL重放，不会在磁盘留下`-wal/-shm`旁文件；已实测`mode=ro`单独使用会在WAL库上创建旁文件，故必须immutable）→④才connect并执行任何PRAGMA/migrate。预检发现`max(schema_migrations.version)>LATEST`即抛`SchemaVersionError`；版本表不存在（全新库）静默放行交给内层migrate门禁。`__init__`任何一步失败都关闭已建立的连接再抛出。复核反例（raw sqlite3构造DELETE-journal未来库，SHA256前后比对）：文件字节不变、无`-wal/-shm`、原数据完好（test_future_delete_mode_database_refused_bytes_unchanged；WAL版同样通过）。
- **资金/事件对账**：新增`_replay_account_ledger`——按seq重放单账户全部事件（deposit/withdraw/reserve/release按amount；fill_buy/fill_sell从payload quantity与note中fee/price复算现金与移动平均成本，quantize 0.0001与Ledger一致），返回cash/reserved/positions/max_seq。`verify_database`对每个账户对账五项：cash、reserved_cash、Σactive预留==reserved、持仓quantity+avg_cost（对比快照payload）、version==max(seq)，结果入`accounts_reconciled`，`ledger_ok`并入`ok`——物理完好但账目不平的副本不再ok=True。T+1 availability刻意不重放（需市场profile知识），对账范围如实记录。
- **正反例补齐（全部临时库）**：合格副本对账通过（test_verify_database_reconciles_real_books，真实Ledger全事件流：入金/买成交/预约/T+1滚动/卖成交/释放/出金+orders/fills引用闭包）；篡改现金（UPDATE cash='999'→ok=False，detail给出stored/expected）、篡改持仓快照quantity（新增test_verify_database_rejects_tampered_position）、激活预留active=1（test_verify_database_rejects_inconsistent_active_reservation）、删最大seq事件（test_verify_database_rejects_missing_event）均被拒绝；孤立成交/悬空引用由既有引用闭包检查覆盖（fills_without_order等计数）。
