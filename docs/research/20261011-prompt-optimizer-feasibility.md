# 条件式提示自动优化可行性评估报告

日期：2026-10-11。关联：[TASK-20261011-09](../tasks/TASK-20261011-09-评估条件式提示自动优化.md)、[ARCH-010](../architecture/10-prompt-evaluation.md)。
本报告针对是否在 TradeMind 中引入第三方提示词自动优化框架（如 Promptfoo、DSPy GEPA）进行技术、安全、预算与协议可行性论证。

---

## 1. 评估背景与核心目标

根据 [提示评测需求 F6](../requirements-prompt-evaluation.md) 和 [ARCH-010 架构设计](../architecture/10-prompt-evaluation.md)，在完成离线提示评测器（TASK-20261011-06）、失败审计扩展（TASK-20261011-07）以及版本晋级门禁（TASK-20261011-08）后，需评估是否引入自动化提示优化工具对策略提示进行迭代优化。

评估原则：
1. **真实成本与预算门禁优先**：任何优化调用必须受控于单日调用限额与费用门禁，严禁绕过账本预算或造成凭据泄露；
2. **硬风控不可协商**：提示词优化仅限调整自然语言表达与少样本示例，严禁修改输出 Schema、硬性风控 Guard 或交易规则；
3. **真实协议兼容性**：必须严格兼容 TypeSafe JEV 官方协议（Choice/Noul 四题结构）与 DeepSeek-flash 九字段输出契约；
4. **务实结论导向**：有充分事实依据的“不采用”结论同样是高质量的研究交付，避免过度工程化。

---

## 2. 外部候选工具与 TradeMind 原生评测对比

| 评估维度 | TradeMind 原生评测体系 (prompt_eval) | Promptfoo (CLI / Web) | DSPy (GEPA / MIPROv2) |
| :--- | :--- | :--- | :--- |
| **运行时依赖与生态** | 零新增依赖，纯 Python 标准库 + 现有 pytest，轻量无侵入 | 需要 Node.js / npm / npx 运行环境，引入跨语言栈维护成本 | 依赖较重 Python 数据科学库（torch / transformers 可选链），包体积与环境复杂度高 |
| **TypeSafe JEV 4题协议兼容性** | 原生深度集成：精确校验 Choice（四动作）与 Noul（概率归一化），支持分题语义与短路断言 | 难以原生支持专有 Choice/Noul 结构；需编写大量定制 JS/Python 断言适配器 | DSPy 签名机制偏向文本问答或简单 Pydantic，难以无缝映射 JEV 专有四题 RPC 请求结构 |
| **凭据安全与网络隔离** | 严格遵循零凭据泄露规范：只消费离线保存响应，`public_call` 强制脱敏，CLI 完全零 HTTP | 工具自带外部遥测与云端服务交互可能；配置管理可能在临时目录导出请求 payload，存在凭据泄露隐患 | 优化循环需要大量实时在线调用；如果配置不当容易绕过本地回环代理或污染测试凭据 |
| **预算控制与单日开销** | 严格限制于现有模型调用预算，按上海自然日重置，每笔调用精确扣减与审计 | 缺乏与 TradeMind 本地 SQLite 账本的预算联动；多轮笛卡尔积测试易造成 API 额度超支 | 自动提示探索算法（如 GEPA）会自适应触发数十至上百次 LLM 调用，调用成本和延迟不可控 |
| **热路径与风控边界** | 仅离线运行；评测结果与生产 OMS 彻底解耦，无账户写权限 | 仅支持离线测试生成；但与系统现有 `strategy_planner` 状态机制割裂 | 框架倾向于在线替换 Module 逻辑，若接入生产热路径存在不可控的非确定性风险 |
| **过度拟合风险防范** | 严格隔离合成工程集与时间切分真实留出集；必须通过人工晋级核验（F5） | 需手动管理数据集切分，无法自动保障时间序列前瞻偏差（Lookahead Bias）隔离 | 自动优化器极易对有限评估集产生过拟合，产生表面高分但泛化极差的脆弱提示词 |

---

## 3. 核心评估结论与决策

### 结论：**明确不采用（Do Not Adopt）外部自动提示优化框架**

**关键事实与原因**：
1. **协议不适配**：TradeMind 采用独特的双模型分工链路（DeepSeek-flash 低频计划 + TypeSafe JEV 快速四题决策）。现有的 Promptfoo 与 DSPy 均以通用对话式 LLM 为主，无法低成本适配 JEV 的专用 Choice/Noul 概率题型。
2. **预算与安全风险**：DSPy 等自动化优化器通过多轮模型交互反向修改提示，在 A 股日内小资金（500 元本金）场景下，自动优化消耗的 API 费用很可能远超过其所带来的潜在滑点与佣金优化收益，且存在绕过单日限额门禁的风险。
3. **原生体系已完备**：TradeMind 现已落地完备的工程体系：
   - 24 例固定标签案例集（`cases.json`）；
   - 零网络、无写权的离线评测器（`evaluate_prompt_cases.py`）；
   - 失败分类审计（`audit_archive_failures`）；
   - 版本注册与晋级/回滚校验机制（`evaluate_promotion_eligibility`、`verify_version_rollback`）。
   这套轻量级原生机制完全满足当前确定性评测与版本管理需求，无需额外引入笨重的第三方框架。

---

## 4. 后续策略与行动指南

1. **坚持人工在环与受控迭代**：提示词变更遵循“单因素修改 $\to$ 离线案例集回归 $\to$ 真实档案留出验证 $\to$ 显式版本晋级”的标准流程；
2. **保留架构边界**：不把自动优化加入每分钟交易热路径，保持交易三方职责（模型出意图、程序出事实、Guard 硬否决）与 500 元小资金隔离；
3. **关闭条件分支**：TASK-20261011-09 达成预定研究目标，结论明确，无需在后续阶段拉起自动优化器原型开发。
