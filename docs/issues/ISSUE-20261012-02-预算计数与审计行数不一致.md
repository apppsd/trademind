# 模型预算请求计数与调用审计行数不一致

## 问题表现

2026-10-12 真实 paper 运行中两次观察到两个计数口径对不上：

1. 上午 09:47～09:49 试跑：运行报告 `paper-49ce589feba34fd7b8cd8177ddd4f931.json` 的调用列表 3 条，但当日预算 used 4（probe 2 / strategy 2）。
2. 全天日报（`data/runtime/container/daily-reports/paper-t0-container/2026-10-12.md`）：预算请求数 14（probe 6 / strategy 8），模型调用审计行 10 条。日报"口径与未确认内容"一节已如实标注该差异。

## 影响

- 费用估算与每日预算门禁的可审计性下降：预算计数（计费用/额度）与审计行（留痕证据）不一致时，无法确认是多计预算（偏保守）还是漏记审计（证据缺失）。
- 不影响交易安全方向：预算是上界预留，多计只会更保守；但若是审计漏记，则真实模型行为证据不完整，影响 Task08 对照校准与真实验收的可信度。

## 环境

2026-10-12，paper 容器（`jev_fast_decision` profile），deepseek-flash + jev-1.13.0，当日共五轮运行。

## 复现方式

对比 `data/runtime/container/paper-runs/*.json` 中 `model_call_records` 条数与 `model_budget.used`（probe/strategy 分项），再对照日报模型调用表行数。

## 原因分析（2026-10-15定位确认）

两个口径测量对象不同，**不是漏记也不是多计错误**：

- **预算 `used` = 计费HTTP请求数**（`daily_budget._reserve` 在每次传输前预约时 +1）。DeepSeek 的 JSON 格式修复重试在同一次 `complete()` 内**再次预约**（`models/deepseek.py` 修复循环每次 `continue` 都 `reserve_request`），一次修复=2次计费请求。
- **审计行 = 逻辑调用留档**（一次 `complete()`/`evaluate()` 恰好一行，无论内部重试），实际请求次数记在行内 `attempts` 字段（修复行 attempts=2；预算耗尽拒绝行 attempts=0 且消耗0）。
- 候选方向核验：**"失败/超时只进预算不进审计"不成立**——deepseek 失败路径（429/HTTP≥400/timeout/空输出/无效JSON/预算拒绝）与 JEV `finally` 均写审计行；**worker排空边界非系统性根因**（预约与留档同在 provider 调用内同步完成，硬杀进程才可能丢行，属有界残余，预算本就是上界口径）。
- 复原核对：10-12全天 14 = 10行中6行探针(attempts=1) + 4行策略(attempts=2)；上午 4 = 2探针 + 1策略(修复重试attempts=2)。**恒等式 `used == Σ(审计行.attempts)` 在所有消耗预约的路径上成立**，可作核对口径。

## 最终解决方法

按Task12-05验收标准选项b执行（口径语义化，不改计数行为——预算必须按计费请求封顶，审计必须保留决策级证据，合并会丢一边）：`reports/daily.py` 模型调用节明确区分并展示三值——`requested_count`（计费请求数）、`audit_rows`（留档调用数）、`audit_attempts`（行内尝试合计），两者不等时输出显式中文说明（"预算请求数按HTTP计费请求累计，审计行数按逻辑调用留档（含JSON修复重试）"）及 `count_semantics` 字段；中文日报同步渲染。该标注与调和随2026-10-12中文日报实现落地。

## 验证结果

resolved（2026-10-15收口确认）。钉住测试（既有，本轮核验仍通过）：
- `tests/test_daily_report.py::test_budget_used_and_audit_attempts_reconciliation`——精确复现10-12全天（10行/used=14/attempts合计14），断言口径字段、中文警告与渲染行。
- `tests/test_paper_run_and_provider_attempt_accounting_on_failures`——修复重试(attempts=2,used+2)、超时(+1且有审计行)、预算拒绝(attempts=0,used不变)。
- `tests/test_t0_runtime_repairs.py::test_repair_attempts_each_consume_persistent_budget`——修复预约持久化。
全量577 passed/0 failed（2026-10-15）。历史运行数据不改写；两份原始证据（paper-49ce…报告、10-12日报）按日期理解。

## 剩余风险

若根因是审计漏写，历史真实调用证据可能永久缺失，只能靠预算计数保守估计。
