## 问题表现
auto-paper.lock只约束Linux自动监督器，helper脚本检查特定Docker标签。直接runner/API/Pipeline入口没有统一按数据库/账户身份的writer租约；同一账户两个Pipeline均能完成初始化。

证据级别：已确认约束可绕过；并发损坏未验证。本轮仅分析，尚未实施修复。

## 影响
包装脚本之外的手动启动、两个不同启动入口竞态或多API进程可绕过系统单writer假设。SQLite事务和Ledger.atomic现有版本刷新有保护，但不能当成模型worker、恢复和进程生命周期互斥；本轮没有验证账户损坏或重复成交。

## 最终解决方法
2026-10-14 由 [TASK-20261013-14](../tasks/TASK-20261013-14-统一账户写入进程互斥.md) 实施修复（设计见[ARCH-017](../architecture/17-writer-lease.md)）：
- 新增`execution/writer_lock.py`：按（规范化库路径+账户）的跨进程写租约，实现为数据库旁`.writer.lock`文件上的字节范围锁（Windows msvcrt非阻塞 / POSIX fcntl.flock）。内核在持锁进程死亡时自动释放——无陈旧PID、无任意删锁；锁文件永不删除/截断（unlink竞争会在同一inode产生两写者）；holder元数据仅诊断，永不用于陈旧判断。
- 取得时机：Pipeline构造即取租约，先于数据库打开/恢复/迁移/付费预约；auto paper子进程经同一构造入口统一覆盖。第二写者抛`WriterLockHeld`→runner输出JSON失败退出码1，且全程未打开数据库（零调用/零写入）。
- 移交/释放：serve（工作台）前runner显式释放——报告路径只读不占租约；同库多账户仍可并行（跨账户一致性由SQLite事务保留）；`:memory:`无非进程租约；非本地URL拒绝。
- 原fcntl auto-paper.lock与Docker标签检查保留为部署层辅助，业务级互斥以本租约为准。

已验证（2026-10-14，Windows / Python 3.12，真实OS子进程，非Mock）：

原验证记录：
