# 分钟行情超时后台请求缺少并发边界

## 性质与影响
这是现有“超时弃置不可取消SDK请求”策略的资源边界改进，不是推翻caller有界等待。每轮等待有界，但超时线程仍在运行；后续退避到期会再次为同一源发起请求，没有进行中数量/并发槽位约束。长时间卡住的SDK会与新恢复探针重叠，增加线程/连接占用，复用同一adapter的请求也可能并发。尚未证实真实SDK永久卡死或生产内存泄漏；日请求上限与进程退出仍限制总暴露，不能宣称无限运行必然无限泄漏。

## 根因与代码
src/trademind/market/router.py：_bounded_fetch每次创建daemon Thread并join(timeout)，超时只抛TimeoutError；没有记录该worker的在途生命周期。_source_skip_reason仅管日计数/失败退避，到期不检查旧worker；主源与_maybe_cross_check共享同一启动helper，资源容量应共同纳入。每日4000次和每轮3源是请求/轮次限制，未对当前实际在途数给出独立上限。当前文档明确SDK不能强制取消，实施不能假装超时即取消。

## 隔离复现（Task17-12）
复用tests/test_minute_source_routing.py.router_with/FakeClock/FakeSource。FakeSource.get_minute_bars仅在Event.wait阻塞，不访问网络；配置per_source_timeout=.005s、round=.02s、failure_backoff60/max900、daily_request_limit4000。对公开get_minute_bars调用8次，每次模拟单调时钟推进901秒使正常退避到期。每次caller按时返回RuntimeError，但活跃trademind-minute-fetch线程数依次1/2/3/4/5/6/7/8，源calls与请求计数均8。时间推进是离线模拟，不是生产已等两小时的证据。
finally显式Event.set并join所有新增测试worker，剩余0。既有路由25项通过；未检测到该资源约束。

## 最终解决方法与验证（2026-10-17，工程口径）

由Task17-13在router层实施，[ARCH-023](../architecture/23-minute-request-inflight-capacity.md)记录资源边界：`MinuteRoutingPolicy`默认全路由4个、每源1个在途请求；主源与观察在计数前原子申请无队列槽位，满员立即busy并尝试有容量的后续pref。busy不消耗每日请求、观察次数或观察节奏。超时worker继续持槽至实际返回/异常，`finally`幂等释放；迟到结果仅写原调用局部box，不修改缓存、选源、health或divergence。`close(timeout_seconds)`拒绝新分钟SDK调用并在真实时限内join，False表示仍有活跃请求，不宣称强制取消。

原公开路由Event反例修复前8次恢复为active=8/calls=8，修复后逐次均为active=1/calls=1，finally释放并join后0。新增5项覆盖全路由上限、健康备用、观察busy/恢复、日切、异常释放、迟到隔离及有界关闭；路由套件30 passed、相关八套件112 passed、全量608 passed/0 failed。真实SDK、容器资源与盘中效果未验，未改配置/部署或发真实行情请求。
